# Vicmap Product Data Validation

## Purpose

This directory contains the validation workflow for the product-facing Vicmap data.

The validation script checks whether the wrangled data is structurally valid, spatially within the selected councils, consistent with the product classification rules, and suitable for use by the application.

The current product scope includes:

- City of Melbourne
- City of Melton
- City of Monash

## Validation script

`validate_vicmap.py` validates the outputs generated by:

`pipeline/wrangling/wrangle_vicmap.py`

Run the validation script from the project root:

```powershell
python pipeline/validation/validate_vicmap.py
```

The script stops with an error if a required validation rule fails.

## Input files
The script reads the following files:
- data/processed/vicmap/vicmap_app_ready.csv
- data/processed/vicmap/vicmap_fallback.csv
- data/raw/boundaries/vicmap_lga_2026-08-26.geojson
- data/validation/vicmap/vicmap_product_review.csv
The product review table contains completed manual decisions and supporting source URLs. These decisions are checked against the generated product outputs.
## Validation checks
### 1. Table structure
Both product outputs are checked for:
- required columns;
- non-empty and unique place_id values;
- non-empty display names;
- valid numeric coordinates;
- valid longitude and latitude ranges; and
- councils outside the defined product scope.

### 2. Product rules
The script confirms that:
- all app-ready records have an include decision;
- all fallback records have a fallback decision;
- app-ready records use one of the seven approved activity categories;
- Melbourne, Melton and Monash are represented;
- no record appears in both product outputs.
The seven approved activity categories are:
- playground
- park_and_garden
- sports_ground
- court
- trail_access
- skate_bmx
- picnic_day_use

### 3. Manual review decisions
Completed decisions from vicmap_product_review.csv are checked against the product outputs.
The validation confirms that:
- excluded and duplicate records do not remain in the product outputs;
- fallback decisions appear only in the fallback table;
- retained records appear in the app-ready table; and
- reviewed name and category corrections have been applied.
A reviewed source record may no longer exist after a future API refresh. This is treated as a stale review rule rather than an automatic validation failure.

### 4. Spatial validation
App-ready and fallback coordinates are converted to spatial points and compared with the Vicmap LGA boundary snapshot.
The script verifies that:
- every product record falls inside one of the selected councils; and
- the spatially matched council agrees with the record's lga_name.
Points located exactly on a council boundary are accepted.

### 5. Quality summaries
The script reports:
- app-ready record counts by council;
- activity-category coverage by council;
- source-name and generated-name counts;
- fallback counts; and
- fallback feature subtypes.

### 6. Review candidate detection
The script generates:
data/validation/vicmap/vicmap_product_review_candidates.csv
Records are flagged using deterministic risk rules, including:
- duplicate display names at the same location;
- multiple records in the same category at the same location;
- possible restricted access associated with schools or childcare facilities;
- possible club membership, booking or fee requirements;
- generic or poorly formatted display names;
- ambiguous destination names; and
- automatically generated display names.
Candidates are assigned one of three priorities:
- high: likely access, duplication or suitability risk;
- medium: requires a clearer destination or classification decision;
- low: suitable for optional name enrichment.
Records already resolved in the formal product review table are not reopened.

## QA sample
The script also generates:
data/validation/vicmap/vicmap_app_ready_qa_sample.csv
This is a reproducible sample of up to three records from every council and activity-category combination. It supports manual spot-checking without requiring every app-ready record to be reviewed individually.
The sample includes fields for:
- QA status;
- review notes;
- evidence URL; and
- date checked.

## Current validation result
For the current data snapshot:
- App-ready records: 2,859
- Fallback records: 101
- Formal review decisions: 74
- QA sample records: 51
- High-priority unresolved candidates: 0
- Medium-priority unresolved candidates: 0
- Low-priority name-enrichment candidates: 700
All 700 remaining candidates were flagged only because their display names were generated from source attributes. They are retained as a non-blocking name-enrichment backlog and do not represent confirmed access, duplication or classification problems.
The complete validation workflow passed successfully.

## Interpretation of outputs
vicmap_app_ready.csv contains the records currently approved for normal product recommendations.
vicmap_fallback.csv contains potentially useful places that should not be presented as unrestricted recommendations because access, fees, booking requirements or operating conditions may vary.
The validation files are QA and audit artifacts. They are not intended to be loaded directly by the application.

##Reproducibility
Validation should be rerun whenever:
- a new Vicmap source snapshot is downloaded;
- wrangling or classification rules change;
- the selected council scope changes;
- manual review decisions are updated; or
- processed product outputs are regenerated.
A successful run ends with:
Vicmap product validation completed successfully.
